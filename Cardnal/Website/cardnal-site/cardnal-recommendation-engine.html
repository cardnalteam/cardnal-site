Recommendation Engine

How Cardnal decides.

The logic behind every recommendation — objective card data, the user's stated goals, and how the two combine. No UI, no interface decisions. Where we don't know yet, it says so.

00

Purpose & Scope

This document defines how Cardnal decides which card wins. It contains no UI. Where the answer is "we don't know yet", it says so rather than inventing a mechanism.

What the engine must do

  1. Identify the merchant from the page.
  2. Assign a category, with a confidence level.
  3. Compute what each card in the wallet would earn.
  4. Rank them by objective earn, then re-rank by the user's stated goals.
  5. Break ties deterministically, and compare to the user's default.
  6. Produce a one-sentence reason — or decline to recommend.

The two halves of a recommendation

Cardnal ranks on two kinds of information, and they must never be conflated in code or in copy.

Objective card dataUser preferences
ExamplesReward rate, category, cap, annual fee, FX fee, network, active offerCash vs. points, welcome-bonus priority, preferred ecosystem, FX avoidance
SourcePublished issuer terms, authored by usStated by the user in onboarding or Settings
Truth statusVerifiable. Wrong = a bug.Not verifiable. Wrong = we misheard them.
Changes whenIssuer changes terms; ruleset version bumpsUser changes their mind; takes effect immediately
StoredRulesetUserState.goals

Why the separation is load-bearing

If a recommendation is wrong because a rate is wrong, that's our fault and we fix the ruleset. If it's "wrong" because the user's goals changed, that's not an error — it's a setting. Collapsing the two into one score makes it impossible to tell which is happening, and impossible to explain the answer in the two different registers the user needs to hear.

Design constraints

ConstraintConsequence
Rules-based, not learnedEvery recommendation must be explainable in one sentence. A model that can't articulate why fails the product requirement. No ML in v0.1.
Runs client-side200ms budget from detection to answer. The ruleset is cached; the network is an enhancement, not a dependency.
No transaction dataWe can't observe spend, so caps and cycle progress are user-declared or unknown. Never inferred.
Abstention is a valid output"We don't know" is a first-class result, not an error. Silence beats a wrong answer.
DeterministicSame inputs → same output, always. No randomness, no A/B in the ranking path.
The engine's real job is knowing when to shut up

Picking the highest number is trivial arithmetic. The engineering difficulty is in the four questions around it: is this the right merchant, is this the right category, is this rule still true, and is the difference big enough to bother the user. Most of this document is about those four.

01

The Pipeline

Eleven stages, each able to abort. An abort is not a failure — it produces a defined non-recommendation state that the UI already has a design for.

page→ identify merchant→ assign category→ load rules→ compute earn→ apply caps→ rank→ apply goals→ compare default→ explain
#StageCan abort withBudget
1Identify merchantno_merchant<10ms
2Assign categoryno_category<5ms
3Load ruleseterror, stale<20ms
4Filter walletno_cards, all_paused<1ms
5Compute earn per card—<5ms
6Apply caps & fees—<2ms
7Rank by objective earnall_equal<2ms
8Apply user goals—<2ms
9Break ties—<1ms
10Compare to default—<1ms
11Generate explanationerror if reason is null<1ms

Order total extraction runs in parallel with stages 1–7 and never blocks them. If it resolves late, the delta fades in. If it never resolves, the recommendation still ships without one.

02

Merchant Identification

InputDescription
url.hostnamePrimary signal. Normalised: lowercase, strip www., strip country suffix where the mapping says it's safe.
url.pathnameSecondary. Distinguishes marketplaces and sub-brands, e.g. /wholefoods on an Amazon domain.
document.titleTertiary, low trust. Used only to raise confidence, never to establish identity alone.
merchantMapCurated domain → merchantId table shipped in the ruleset.
→ output{ merchantId, name, confidence: high | medium | low } or null

Edge cases

  • Marketplace sellers. A third-party seller on Amazon still transacts as Amazon. Match the platform, not the seller.
  • Payment processors. If the hostname is a processor (Shopify checkout, Stripe-hosted), the merchant is the referring site. Carry identity across the redirect or abort.
  • Subdomains. smile.amazon.com, music.amazon.com — same merchant, potentially different category. Match merchant on domain, category on path.
  • Regional TLDs. amazon.co.uk is the same merchant but a foreign transaction for a US card. Merchant matches; the FX flag is set separately.
  • Unknown domain. Abort with no_merchant. Do not fuzzy-match, do not guess from the title alone.
  • Domain squatting / lookalikes. Exact-match only. A near-match to a known merchant is a non-match, deliberately.
Exact matching only in v0.1

Fuzzy merchant matching sounds helpful and is the fastest route to a wrong recommendation on a phishing lookalike domain. The curated map is the whole mechanism. Coverage grows by adding entries, which is boring, safe, and measurable — and "Request this store" gives you the demand signal for which entry to add next.

03

Merchant Category

InputDescription
merchantIdResolved in stage 1.
categoryMapmerchantId → categoryId, plus optional path overrides.
url.pathnameApplies a path override where one exists.
mccHintOptional. If a future data source supplies an MCC, it takes precedence over the map.
→ output{ categoryId, label, source: domain | path | default, confidence }

Edge cases

  • Multi-category merchants. Amazon is online retail; Amazon Fresh is groceries; Whole Foods is groceries. Path overrides handle this. Where the path is ambiguous, fall back to the merchant's primary category and mark confidence medium.
  • Issuer disagreement. Issuers classify the same merchant differently — Target may code as a superstore for one card and groceries for another. Category is per-issuer, not global. The map is keyed (merchantId, issuerId) where they differ.
  • Warehouse clubs, superstores, gas at grocery. Classic ambiguity. When two categories are plausible, use the one the issuer's own terms name, and if the terms are silent, take the lower-earning interpretation.
  • No category. Abort with no_category — every card earns base rate, which is the all_equal outcome.
  • Category changed mid-session. Recompute silently; never re-animate.
The conservative-interpretation rule

When a category is ambiguous and the issuer's terms don't settle it, assume the interpretation that earns less. Over-promising a bonus rate that doesn't post is the single fastest way to lose a user's trust permanently — they'll see the statement weeks later and remember that we were wrong. Under-promising costs nothing.

04

Card Reward Rules

The ruleset is versioned, immutable data. It is authored by us from published issuer terms, never scraped at runtime, and never inferred.

// one card in the ruleset
{
  cardId: 'chase_prime_visa',
  displayName: 'Prime Visa',
  issuer: 'chase',
  network: 'visa',
  currency: 'cash',            // 'cash' | 'UR' | 'MR' | 'venture_miles' | …
  annualFeeCents: 0,
  foreignTxFeePct: 0,
  baseRate: { value: 1, unit: 'percent' },
  bonuses: [
    { categoryId: 'amazon',   value: 5, unit: 'percent', cap: null },
    { categoryId: 'dining',   value: 2, unit: 'percent', cap: null },
  ],
  rotating: null,
  termsUrl: 'https://…',
  ratesVerifiedAt: '2026-08-01'
}
FieldRule
currencyDetermines comparability. Two cards are only directly comparable if this matches. See section 09.
unitpercent for cashback, multiplier for points. Never mixed on one card.
capnull means uncapped. A cap object carries { amountCents, period, resets }.
ratesVerifiedAtPer-card, not per-ruleset. One stale card shouldn't age the whole file.
termsUrlRequired. Every rate must be traceable to a published source.

Precedence

  1. Merchant-specific bonus (e.g. 5% at Amazon on the Amazon card).
  2. Active rotating category, if enrolled and within cap.
  3. Standing category bonus (dining, groceries, travel).
  4. Base rate.

Highest applicable rate wins; bonuses never stack unless the issuer's terms explicitly say they do, in which case the ruleset encodes it as a single combined rate rather than summing at runtime.

05

Base & Bonus Rates

InputDescription
cardRuleset entry.
categoryIdFrom stage 2.
merchantIdFor merchant-specific bonuses.
orderTotalCentsOptional. Absent for browse-time recommendations.
→ output{ rate, unit, currency, appliedRule, earned? }

Edge cases

  • No order total. Return rate only, earned undefined. Everything downstream must tolerate this.
  • Rate is a range (some cards vary by tier). Use the lowest in the range and say so in the reason.
  • Promotional / limited-time rates. Not modelled in v0.1. Encoded only if they have a hard end date in the terms; otherwise ignored.
  • Portal-only rates (issuer shopping portals). Excluded from v0.1 — the user isn't in the portal, so the rate doesn't apply.
  • Zero-earn cards. Legitimate; they simply lose. Never filtered out of the comparison.
06

Rotating Categories

InputDescription
card.rotatingQuarter definitions with activation requirement.
todayDetermines the active quarter.
user.enrolled[cardId][quarter]User-declared. We cannot see enrolment.
→ outputActive bonus rate for this quarter, or base rate if not enrolled / unknown

Edge cases

  • Enrolment unknown. This is the common case. Treat as not enrolled and use base rate — then, if the bonus rate would have won, surface it as a secondary line: “If you've activated this quarter's 5% category, Freedom Flex earns more.” Never silently assume enrolment.
  • Quarter boundary. Categories change at 00:00 on the first day of the quarter in the issuer's timezone, not the user's. Store the boundary explicitly per issuer.
  • Quarter not yet published. Issuers announce roughly a month ahead. If the upcoming quarter is unknown, the card falls to base rate on that date and the ruleset is flagged for update.
  • Activation deadline passed. If the user never activated and the deadline is gone, that quarter is base rate permanently — no prompt.
Rotating categories are the biggest correctness risk in the MVP

They change quarterly, they require activation we can't observe, and they carry caps we can't measure. Getting one wrong produces a confidently wrong recommendation. The safe posture is to treat rotating bonuses as inactive unless the user has told us otherwise, and to present the alternative as a conditional line rather than a claim.

07

Spending Caps

InputDescription
bonus.cap{ amountCents, period, resets } from the ruleset.
user.declaredSpend[cardId][categoryId]User-declared, optional. Blank in most cases.
orderTotalCentsTo detect a purchase that straddles the cap.
→ outputEffective rate after cap logic, plus a capState flag

Edge cases

  • Spend unknown (default). Assume the cap is not reached. Use the bonus rate. Do not warn — an unprompted “you may have hit your cap” on every purchase is noise.
  • Declared spend ≥ cap. Drop to base rate for that category and say why in the reason.
  • Purchase straddles the cap. Part earns bonus, part earns base. In v0.1, use the base rate for the whole purchase — the conservative interpretation — and note it.
  • Cap period reset. Reset declared spend to zero at the period boundary and stop applying the cap state.
  • Cap per statement vs. per calendar year. Different issuers differ. Store the period type explicitly; never assume calendar.
Why user-declared and not tracked

Tracking spend against a cap requires transaction data, which requires a bank connection, which is explicitly out of MVP scope. The honest alternative is an optional field on the card row and a conservative default of "not reached". It's imperfect, and it's better than either guessing or building the wrong product to find out.

08

Foreign Transaction Fees

InputDescription
merchant.settlementCurrencyFrom the merchant map, where known.
card.foreignTxFeePctFrom the ruleset.
orderTotalCentsTo size the fee against the reward.
→ outputnetRate = earnRate − foreignTxFeePct, plus an fxApplied flag

Edge cases

  • Currency unknown. The common case for a US-domain merchant. Assume domestic, apply no fee, set fxApplied: false.
  • Foreign merchant, card charges 3%. A 3% FX fee usually outweighs a 2% reward. The net rate can be negative and the ranking must handle that — a card can lose to a 1% card with no FX fee.
  • All cards charge FX. The fee is then common to every option and doesn't change the ranking, but it still belongs in the explanation.
  • FX is the tiebreaker. When two cards tie on earn rate, the one without an FX fee wins — see section 10.
  • Dynamic currency conversion at checkout. Out of scope. Not detectable from the page.
09

Cash vs. Points

The single most consequential decision in this document: Cardnal does not convert points into dollars in v0.1.

Why not just use 1¢ per point?

Because it isn't true, and the error isn't small. A Chase UR point is worth roughly 1¢ redeemed for cash and materially more transferred to a partner — the spread depends entirely on how the individual redeems. Publishing one number turns a redemption preference into an apparent fact, and it would make our maths wrong for most users in one direction or the other. A product whose core promise is "we explain our reasoning" cannot rest on an undisclosed valuation.

Comparability rules

Winner currencyCompared cardComparable?Output
cashcashyesDollar delta.
URURyesPoints delta and multipliers. No dollars.
URMRnoBoth shown, neither declared better.
cashURnoTwo separate lists, winner within each.

Which card is recommended when both a cash and a points card exist?

The cashback winner — with the points alternative named on a secondary line. The reasoning: cash value is certain and immediate, points value is contingent on future behaviour we can't observe. Certainty beats theoretical maximum when we're the ones being trusted.

// comparability is computed, never assumed by the UI
function comparable(a, b) {
  return a.currency === b.currency;
}

// ranking within a currency group only
const groups = groupBy(cards, c => c.currency);
const winners = mapValues(groups, g => rank(g)[0]);
const headline = winners['cash'] ?? highestConfidenceGroup(winners);
"Best overall value" is the exception, and it costs something

Section 10 lets a user choose Best overall value as their goal. That goal is only meaningful if points can be compared to cash — which requires exactly the valuation this section refuses to assume. The resolution: choosing that goal is the user opting in to a disclosed valuation. When it's selected, Cardnal uses a published, per-currency table (baseline: the issuer's own cash-redemption rate, never a travel-blog aspirational figure), shows the figure it used, and lets the user override it. Every other goal leaves cross-currency comparison switched off.

The default valuation is deliberately pessimistic

We value points at the rate the issuer will give you in cash — typically 1.0¢, sometimes 0.6¢ — not at transfer-partner potential. A user who transfers well will do better than we predicted, which is the right direction to be wrong in. Any figure shown carries "at cash-redemption value" next to it.

10

User Preferences

Preferences are the second input to every ranking. They're stated, not inferred, and they're a ranked list rather than a single choice — most people want more than one thing.

The goal set

GoalidEffect on ranking
Cash backcashCash-currency cards get preference weight. Points cards can still win, but only by the override margin.
Points & milespointsTransferable-currency cards get preference weight. Fixed-value points rank below transferable.
Welcome bonuseswelcome_bonusAny card with an active, incomplete bonus requirement gets the strongest weight in the system. See section 11.
Card offersoffersCards with an activated merchant offer matching this merchant get weight. See section 12.
Best overall valuebest_valueEnables cross-currency comparison using the disclosed valuation. Ranks purely on estimated dollar value.

Ranked, not exclusive

The user orders up to three goals. Position determines weight:

// weights are multipliers on the objective score
const GOAL_WEIGHT = { 1: 1.00, 2: 0.60, 3: 0.30 };

// example: [welcome_bonus, points, cash]
//   a card advancing a welcome bonus  → weight 1.00
//   a transferable-points card        → weight 0.60
//   a cashback card                   → weight 0.30
//   a card matching none of the goals → weight 0.00 (objective score only)
RuleDetail
Maximum three goalsBeyond three, the weights are too close to change any outcome and the UI becomes a chore.
Minimum oneDefault for a new user is [best_value] — but the onboarding screen asks, so most users never sit on the default.
best_value is exclusiveIt can't be combined with others. It is the "just work it out" option; mixing it with a preference contradicts it.
Changing goalsTakes effect on the next recommendation. Never recomputes history, never notifies.
No goals setBehaves as best_value with cross-currency comparison off — so cash and points rank separately, as in v0.1.

The override rule

Preferences bend the ranking. They must not break it.

A user who prefers points still wants to know when a cashback card earns dramatically more. If the top objective card beats the top preference-weighted card by more than the override margin, the objective winner is recommended anyway — and the explanation says why it overrode the preference.

ComparisonOverride marginExample
Same currency2× the rate, or $10 absolute, whichever is smaller5% cash vs. 2% cash — recommend the 5% even if the 2% card is the preferred product.
Cross-currency3× the rate5% cash vs. 4x points: 5% doesn't clear 3× of a 1x-equivalent baseline, so the points preference holds.
Welcome bonus activeNo override.A bonus worth hundreds outweighs any per-purchase rate difference. Section 11.

This is the mechanism behind "don't recommend my Amex unless it's substantially better" — substantially is 2× same-currency, 3× cross-currency, and it's a published number rather than a feeling.

InputDescription
user.goals[]Ranked list of 1–3 goal ids.
candidates[]Cards with objective scores from stage 7.
valuationEnabledTrue only when the goal is best_value.
→ outputRe-ranked candidates, each with { objectiveScore, goalWeight, finalScore, overrodePreference }

Edge cases

  • No card matches any goal. All weights are 0; ranking is purely objective. Explanation omits the preference clause entirely.
  • Every card matches the top goal. Weights cancel out; ranking is objective again. Do not manufacture a preference reason.
  • Goal is unsatisfiable here (e.g. offers but no offers at this merchant). Fall through to the next goal in the list silently.
  • Preference and objective agree. The common case. Lead with the objective reason; mention the preference only if it's the tiebreaker.
  • Override triggered. overrodePreference: true — the explanation must acknowledge it, never silently contradict what the user asked for.
11

Welcome Bonuses

The highest-value signal in the whole engine, and the one built on the shakiest data. A $900 bonus dwarfs every per-purchase rate difference — which is exactly why the tracking has to be honest about what it doesn't know.

InputDescription
user.bonusProgress[cardId]User-declared: { requiredCents, spentCents, deadline }.
orderTotalCentsTo compute remaining after this purchase.
todayAgainst the deadline.
→ output{ active, remainingCents, daysLeft, atRisk, wouldComplete }

Edge cases

  • No bonus declared. The overwhelmingly common case. The goal simply has nothing to act on; fall through to the next goal.
  • Deadline passed. Mark inactive, stop weighting, and tell the user once so they can clear it.
  • Requirement already met. Mark complete, stop weighting. Prompt once to confirm and remove.
  • This purchase completes it. Strongest possible signal — say so explicitly: \u201cThis purchase completes your welcome bonus.\u201d
  • At risk — remaining spend exceeds what's plausible in the days left. Still weight it, but do not create urgency in the copy. State the facts.
  • Multiple active bonuses. Weight the one with the nearest deadline. Never split a purchase across two.
  • Spend tracking drifts. We only know what the user told us. Show the declared figure and its date in the explanation so they can sanity-check it.
We cannot track bonus progress ourselves

Progress requires transaction data, which requires a bank connection, which is out of MVP scope by deliberate choice. So the number comes from the user: a card row field reading "spent about $X of $Y by {date}". Blank means no active bonus — never assume one, and never estimate progress from anything.

Why this goal has no override

Every other preference bends when the objective difference is large enough. Welcome bonus doesn't, because the magnitudes aren't comparable: 3% versus 5% on a $284 purchase is $5.68, while completing a bonus is often several hundred dollars. When a bonus is genuinely active and incomplete, the per-purchase rate is close to noise.

12

Card Offers

Merchant-specific offers (Amex Offers, Chase Offers, and similar) can beat any base category rate — 10% back at one merchant for one month. They're also the most volatile data in the system and the hardest to verify.

InputDescription
user.activatedOffers[cardId][]User-declared: { merchantId, value, unit, expires, minSpendCents }.
merchantIdFrom stage 1.
orderTotalCentsTo check the offer's minimum spend.
→ output{ hasOffer, offerValue, meetsMinimum, expiresInDays }

Edge cases

  • Offer not activated. Most issuer offers require activation. If the user hasn't marked it activated, treat it as unavailable and mention it conditionally at most.
  • Minimum spend not met. Offer doesn't apply. Do not tell them to spend more to reach it — that's the opposite of our job.
  • Offer expired. Drop it silently and clear the record.
  • Offer stacks with the base rate. Usually true, but issuer-dependent. Encode stacks: boolean per offer; when unknown, assume it does not stack.
  • Multiple cards have an offer here. Rank by total value after the base rate, not by offer size alone.
  • Offer is a statement credit, not a rate. Model as a fixed cents value, not a percentage.
Offers are v0.2's weakest data and should ship last

They change weekly, they're per-user, they require activation we can't see, and they're not published in any structured form. For the MVP this is a user-declared field with no automated source, and the goal should be presented as such: "Cardnal will factor in offers you've told us about." If that feels too manual to be useful, the honest move is to cut the goal from the launch set rather than fake the coverage.

13

Preference-Weighted Ranking

How the two halves combine. The objective score is computed first and stays inspectable; preferences multiply it, they never replace it.

// stage 7 — objective, preference-free
objectiveScore = earnedCents ?? (netRate × 100)     // cents where a total exists

// stage 8 — apply goals
goalWeight     = maxWeightOfMatchingGoals(card, user.goals)   // 0, 0.30, 0.60 or 1.00
finalScore     = objectiveScore × (1 + goalWeight)

// override guard — objective truth wins when the gap is large
if (topObjective.objectiveScore >= topFinal.objectiveScore × OVERRIDE_MULTIPLE
    && !topFinal.hasActiveWelcomeBonus) {
  winner = topObjective;
  winner.overrodePreference = true;
}

Worked example — your restaurant case

Purchase: $200 at a restaurant. Wallet: Amex Gold (4x MR dining), Card B (5% cash dining), Card C (2% cash, $300 remaining on an active welcome bonus).

User goalsWinnerWhy
[cash]Card B5% cash is both the objective cash winner and the preferred currency. $10.00 back.
[points]Amex Gold800 MR. Card B's 5% doesn't clear the 3× cross-currency override margin, so the preference holds.
[welcome_bonus, cash]Card CBonus is active and incomplete. No override applies. $200 of $300 remaining is cleared.
[best_value]Card BAt cash-redemption valuation, 800 MR ≈ $8.00 vs. $10.00 cash. Shown with the valuation stated.
[points]Card B (override)If Card B earned 15% instead of 5%, it clears 3× and wins despite the points preference — explanation acknowledges the override.
This is the part that makes Cardnal more than a rate calculator

Four different correct answers to the same purchase, each explainable in one sentence, each traceable to something the user actually told us. A database of 5x categories can't produce that.

14

Tie-Breaking

InputDescription
candidates[]Every non-paused card with a computed net rate.
currencyGroupRanking happens within a group, never across.
orderTotalCentsOptional; changes sorting from rate to absolute earn where present.
→ output{ winner, alternates[], isTie, tiebreaker }

Edge cases

  • Sort key. With an order total, sort by absolute earn. Without one, sort by net rate. These can disagree when caps straddle — prefer absolute earn.
  • Tie threshold. Two cards tie if their rates are within 0.5 percentage points, or their earn is within $0.50.
  • All cards within 0.25pp. Emit all_equal — no winner, no recommendation. Interrupting someone for a rounding difference is a net negative.
  • Single card in wallet. It wins by definition. Flag trivialWin: true so the UI can nudge for a second card instead of pretending it made a choice.
  • Negative net rate (FX fee exceeds reward). Still ranked; may legitimately lose to a lower-earning card.

Tie-breaking, in strict order

  1. No foreign transaction fee — only when the merchant is foreign or currency is unknown-but-suspected-foreign.
  2. No annual fee — a $0 card beats a $95 card at equal earn.
  3. Uncapped over capped — preserves the user's capped headroom for later.
  4. The user's default card — if it's tied for first, it wins. Do not move someone off their habit for zero gain.
  5. Alphabetical by cardId — a deterministic last resort so the same inputs always produce the same output.

When a tie is broken by rules 1–3, the tiebreaker is named in the explanation and the UI shows both cards. Rules 4 and 5 are silent — they're arbitration, not reasoning.

15

Default Comparison

InputDescription
winnerResult of stage 7.
defaultCarduser.defaultCardId, may be null.
orderTotalCentsRequired for a dollar delta.
→ output{ comparable, deltaCents | null, defaultIsWinner, suppressedReason }

Edge cases

  • No default set. comparable: false, suppressedReason: 'no_default'. Every delta suppressed product-wide.
  • Default is the winner. defaultIsWinner: true. The UI says so explicitly — this is a trust-building moment, not a null result.
  • Default is paused or removed. Treat as no default. Prompt once to pick a new one.
  • Cross-currency. comparable: false, suppressedReason: 'cross_currency'.
  • No order total. suppressedReason: 'no_total'. Rate difference may still be described in words.
  • Delta below $1.00. suppressedReason: 'below_threshold'. Computed but not shown.
  • Rounding. Always round the delta down to the cent.
The delta is a claim, and claims need standards

Every dollar figure Cardnal shows is a promise the user will check against a statement weeks later. The suppression rules exist so that the figure is either right or absent. There is no acceptable middle ground where it's approximately right — an “about $11” that arrives as $4 costs the account.

16

Confidence

Confidence isn't decoration — it gates behaviour. Low confidence changes what the product is allowed to say.

LevelEstablished byProduct may…
highExact domain match in the curated map, category from domain or an explicit path overrideShow the recommendation, the delta, and send notifications.
mediumDomain matched, category inferred from a fallback or a merchant with multiple plausible categoriesShow the recommendation and the delta. No notification. State the category source in the explanation.
lowAnything weaker — title-based guesses, partial matches, unresolved redirectsNothing. Treated as no_merchant.

There is no numeric confidence score in v0.1. Three named levels are easier to reason about, easier to test, and don't imply a precision we can't justify. A score would invite thresholds nobody can defend.

Confidence is per-stage and takes the minimum

Merchant confidence and category confidence are tracked separately, and the recommendation's overall confidence is the lower of the two. A perfectly identified merchant with an ambiguous category is a medium-confidence recommendation.

17

Stale Reward Data

InputDescription
card.ratesVerifiedAtPer-card verification date.
ruleset.fetchedAtWhen the client last successfully refreshed.
today
→ output{ ageDays, staleness: fresh | aging | stale | expired }

Edge cases

  • 0–7 days (fresh). Full behaviour, no notice.
  • 8–30 days (aging). Recommendation shown; delta suppressed; amber notice; notifications off.
  • 31–90 days (stale). Recommendation shown at reduced emphasis with an explicit “verify with your issuer” line. No delta, no notifications.
  • >90 days (expired). No recommendation. Show the refresh path only. A three-month-old rotating category is likely wrong.
  • Refresh fails while offline. Age keeps counting; the same thresholds apply. Offline is not an excuse to show stale rates confidently.
  • A single card is stale but others are fresh. Rank without the stale card and note its exclusion, rather than ageing the whole recommendation.
Rotating-category cards age fastest

A card with a rotating bonus should be treated as aging after the quarter it was verified in ends, regardless of day count. A rate verified on March 30th is stale on April 1st.

Preference-aware templates

When a goal changed the outcome, the explanation must say so — in the user's own framing, not ours.

SituationReason string
goal_pointsYou told us you prefer travel points. Earn {multiplier} on this purchase.
goal_cashYou prioritise cash back. This card earns {rate} here.
goal_bonus_progressYou're ${remaining} away from earning your welcome bonus.
goal_bonus_completeThis purchase completes your welcome bonus.
goal_offerYou activated a {offerValue} offer at {merchant} on this card.
goal_best_valueHighest estimated value here — {value} at cash-redemption rates.

goal_unsatisfiableNo {goal} option at this merchant — this is your best card otherwise.
Two registers, never mixed in one sentence

Objective reasons state a fact about the card: "Highest rewards for Amazon purchases." Preference reasons state something the user told us: "You told us you prefer travel points." A sentence that does both becomes long and slightly patronising. Pick the one that actually decided the outcome.

Constraints

  • One sentence, under 60 characters where possible, hard cap 90. It must never truncate in the UI.
  • Names the deciding factor, not the outcome. "Highest rewards for Amazon" explains; "This is your best card" restates.
  • No hedging words — "may", "could", "potentially" — except in the rotating_unknown template, where the conditional is the point.
  • Never references Cardnal. "We think", "Cardnal recommends" adds nothing and consumes the character budget.
  • Templates are versioned with the ruleset, so a rule change and its explanation ship together.

Abstention is a designed outcome with its own return values. Every one of these maps to a screen that already exists in the MVP spec.

The abstention bar is deliberately low

Seven of the engine's possible outputs are "say nothing useful". That ratio is correct for a product that appears uninvited on someone else's checkout page. The cost of a missed recommendation is one lost cent-fraction; the cost of a wrong one is the install. When any stage is uncertain, the whole pipeline abstains.

What abstention must never do

  • Never fall back to "use your default card" as though it were a recommendation. If we don't know, we don't know.
  • Never show a rate we haven't verified for this merchant and category.
  • Never show a dollar figure derived from an assumed total.
  • Never retry silently in a loop — two attempts, then a defined failure state.
